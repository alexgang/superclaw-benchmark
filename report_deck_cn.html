从基准到真实 Agent 工作

From Benchmarks to Real Agent Work

  • 已有：模型性能基准与排行榜已成熟，但衡量的是"模型本身"。
  • 想知道：把模型装进一个真实的混合 agent（SuperClaw）后——每步任务是否被合理路由到云 / 本地？准确率是否保持？本地 PII 是否真的不出机？
  • 缺失：通过 / 失败的分数掩盖了"在哪、为什么坏"。尤其是产品头条宣称的端侧 PII 掩码，从未被独立验证过是否真的生效。
本评估回答四问
① 分解 / 路由是否合理 · ② 准确率是否保持 · ③ 性能（TTFT / TPS / 内存）· ④ 隐私（本地 PII 是否不上云）。以纯云端 MiniMax-M3 为对照基线。

评估方法 · Assessment Methodology

Evidence-Centered Design + 隐匿评估（Stealth Assessment）

证据中心设计（ECD）

能力 → 证据 → 任务。每个任务里嵌入确定性校验点：植入 PII 是否出现在出云载荷 / 输出；数值 / 行数 / exit code 是否匹配 ground truth。

裁判与把关（对齐官方 · 加固）

Claude Opus 4.8（本机 A 内联、SUT 池外、无密钥）逐题打 L2 质量分，每题 2 跑 + 方差重试（差>0.2 → 补到 4 跑取均值）平滑判分噪声；另判 L1 委派正确性（是否路由到预期 sub-agent）；叠加确定性 PII 复读检查。

口径校正：本地模型不同，勿直接对基线
官方本地 = Qwen3-Coder-Next（认证大模型），我们 = Qwen3.5-4B（硬件缩水档）。因此我们的 L2 分数不能套官方 ±0.03 容差；对基线时须换认证本地模型，或明确标注"硬件缩水档"。云端亦不同（我们 MiniMax-M3 vs 官方 GLM-5）。

③ 指标定义（L1 / L2 等）

指标含义取值
L1 委派正确性父 agent 有没有把任务路由到"预期的" sub-agent（local-file-agent / websearch-agent / email-agent / build）——查的是分派对不对，与答案质量无关。对照任务清单里的 expected_delegation。通过数 / 总数（%）
L2 质量分裁判模型按 rubric 给每题打的答案质量分（0–1）；我们用 Opus 4.8，每题 2 跑 + 方差重试取均值。这就是我们说的准确率(accuracy)那一维。0.0 – 1.0（越高越好）
L2 mean ± std一臂内 116 题 L2 的均值 ± 标准差（std 越小=质量越一致）。如 0.91 ± 0.14
L2 / M cloud tok每百万云端 token 买到的质量 = L2 mean ÷（云 token/10⁶）；越高=花的云钱越值。越高越好

核心发现 · Top Findings

1

perf_weight 是偏好旋钮，不是硬开关 — 两端都混合（pw=1.0 仍 72% 本地；脱敏 / 合并类恒全本地）。真正的纯云端基线须禁用本地槽。

2

混合准确率 −16.6pp — Opus 判 Hybrid 54.2% vs Cloud 70.8%，是 4B vs M3 的能力差，非架构缺陷。

3

隐私收益来自"不上云"，非本地更谨慎 — security_manager 掩码未激活；反直觉：本地 4B 输出端复读 PII 更多（7 vs 3），lh06 仅脱敏 1/3 SSN。

4

Token 节省 100% 但有代价 — pw≤0.7 云端 token 0 vs 7,542；代价 = 准确率 −16.6pp + TTFT 1.9× / P95 2.7×。

5

1.2.0 攻克 agent 自动化 — prompt_async 路径使长程 8 任务首次无人值守跑通；但出云掩码验证 + edge 模式两阻塞仍未解。

6

路由由任务类型主导 — 脱敏 / 合并类恒本地、代码 / 预测类恒混合；perf_weight 仅边际加权。

Bottom line：SuperClaw 的价值定位是"隐私优先 + 够用"——靠路由把敏感任务留本地换取隐私，代价是准确率与时延；而产品头条宣称的端侧主动 PII 掩码尚未验证生效。定位它为"私密且够用的 AI PC"，而非与云正面比拼准确率。
